# 需求归一化（Requirement Normalization）

> Gate A 的产物之一。原始输入是混合的：业务目标、教学流程、角色分工、技术约束、数据、话术、运营流程常常揉在同一段文字里。归一化 = 把每条需求拆成可追踪的独立条目，挂到对象/状态/页面上。

## 1. 混合输入的拆解法

读到一段原始材料，按七个桶分离：

| 桶 | 内容 | 去向 |
|----|------|------|
| 目标/价值 | 为什么做（商业主张、教学法目的、家长 aha） | Requirement Ledger 的「规则」列 |
| 流程/步骤 | 谁在何时做什么（阶段表、SOP） | Service Blueprint / 任务流 |
| 角色/分工 | 主教/助教/孩子/后台/家长各自职责 | Service Blueprint 泳道 |
| 角色能力/语言 | 谁能理解什么、不能被要求掌握什么、任务复杂度与升级路径 | Actor Card / Role–Task–Surface Matrix |
| 对象/数据 | 名词性实体及其字段（线索、场次、作品、记忆槽） | ORCA 对象模型 |
| 状态/规则 | 状态机、转换条件、硬约束（铁律、一票否决） | 状态模型 / 不变量 |
| 话术/文案 | 具体说法（孩子话术、换皮、禁词） | 页面规格的文案层，**不进逻辑层** |

规则：逻辑层保留目标、流程、角色分工、角色能力、对象与状态；具体话术在页面规格阶段接管，但逻辑层必须先声明角色语言合同与禁止暴露的技术概念。

## 2. Requirement Ledger（需求台账）

每条需求一行，ID 唯一，贯穿到验收。模板：[../assets/requirement-ledger-template.md](../assets/requirement-ledger-template.md)。

| 字段 | 说明 |
|------|------|
| Req ID | R-001…（按功能域分段） |
| 来源 | Source ID + 章节（见 source-routing 的版本登记表） |
| 需求 | 一句话（客观描述，不含方案） |
| 产品规则 | 由此推导的规则（可执行的判断句） |
| 对象/状态 | 落在哪个对象的哪个状态/属性上 |
| 角色/工作台 | 谁负责、谁消费、落在哪个角色工作台 |
| 页面/组件 | 呈现在哪（Gate C 后填） |
| 验收条件 | 可验证的二元标准 |
| 状态 | 采用 / 待业务方确认 / 不采用（含理由） |

## 3. JTBD 句式（新需求澄清时）

来自 prd-skill 方法，仅用于**没有 rundown 的新方向**（已有 rundown 的需求不另造 PRD）：

```
When [情境], I want [动机], So I can [期望结果].
```

配套用户故事：`As a [角色], I want [动作], so that [收益].`（挂到 Req ID 后）
