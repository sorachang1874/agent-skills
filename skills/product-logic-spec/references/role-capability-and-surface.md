# 角色能力与工作台边界（Actor, Capability & Surface）

> Gate A 的强制产物。它防止“领域模型更干净了，但页面变成只有技术成员看得懂的治理后台”。角色边界必须先于对象导航和页面合同。

## 1. 角色不等于人、账号或职位名

- **人**可以兼任多个角色；**角色**代表一组稳定目标、决策权、知识和责任。
- “教师”“运营”“课程设计者”“管理员”若无法回答具体 Top task、专业能力和交接对象，只是标签，不算完成角色建模。
- 同一账号具有多权限时，可以通过角色工作台、模式切换或专家入口承接；不能把所有配置默认堆在一页。

高风险含混词：课程设计者、内容管理员、后台人员、运营、老师、产品。遇到这些词先拆角色卡。

## 2. Actor Card（每个关键角色一张）

```text
### Actor: {角色名}
- 核心结果：完成后业务世界发生什么变化
- Top tasks：高频 1-3 项；低频/例外项另列
- 使用情境：何时、频率、时间压力、是否课堂实时
- 专业能力：教学/内容/运营/数据/技术等已具备知识
- 不应要求掌握：明确禁止成为前置知识的概念
- 决策权：能决定什么；只能建议什么；必须转交什么
- 可见对象：业务语言下能识别和操作的对象
- 复杂度预算：一次任务允许的步骤、概念层数、配置密度
- 证据需求：完成任务需要看到的业务证据
- 专家升级：超出边界后转交哪个角色/工作台
```

复杂度预算不是固定数字，但必须可检验。例：教研教师可理解“本课保存主角图片，下一课继续使用”，不应以 schema path、Binding、TransformationVersion 和 checksum 作为完成任务的前置知识。

## 3. 三张强制矩阵

### 3.1 Role–Task–Object Matrix

| 角色 | Top task | 业务对象/意图 | 可直接操作 | 只读/摘要 | 必须转交 |
|---|---|---|---|---|---|
| | | | | | |

用途：找出同名角色是否被塞入互相冲突的任务；避免把系统对象所有权误当成用户操作权。

### 3.2 Role–Surface Access Matrix

| 页面/工作台 | 主要角色 | 次要角色 | 默认可见 | 专家模式 | 禁止出现 |
|---|---|---|---|---|---|
| | | | | | |

规则：

1. 每个 Route-level 页面只能有一个主要角色；次要角色只能只读、审核或通过明确模式进入。
2. 面向不同专业语言的角色不得共享同一默认编辑面。例如教研教师与数据契约负责人不能共用一个字段编辑器。
3. “无权限隐藏按钮”不等于完成角色设计；如果页面主体仍是该角色无法理解的对象，应从其导航中移除。

### 3.3 Intent–System Translation Matrix

| 用户意图语言 | 目标角色 | 系统对象/规则 | 自动生成/建议 | 专家可见证据 | 用户侧错误表达 |
|---|---|---|---|---|---|
| | | | | | |

用途：系统底座可以复杂，但目标用户只处理业务意图。例：“下一课沿用上一课的主角图片”可由系统建立 FieldDefinition、producer/consumer Binding 与转换；教师侧只确认保存环节、使用环节和缺失时怎么办。

## 4. 工作台分层原则

先按 **audience / job** 分工作台，再在每个工作台内部选 object-first、task-first 或 lifecycle：

```text
产品
├─ 教学设计台      教研教师：课程目标、课堂环节、话术、教学素材、跨课延续、预览提交
├─ 平台治理台      平台/数据/策略/发布：schema、binding、policy、release、impact
└─ 课堂执行台      授课与运营：开课、推进、恢复、交付
```

一个领域对象可以只有一个系统真源，但可以有多个角色视图：教师编辑“跨课延续意图”，平台治理台查看其编译后的 Binding。**唯一对象家园不等于唯一 UI 表达。**

## 5. 技术复杂度的渐进披露

按目标角色分四层：

1. **任务语言**：默认层，说明要完成什么、为什么、下一步是什么。
2. **业务证据**：课程、环节、素材、影响范围、负责人等可验证事实。
3. **专家解释**：类型、scope、规则版本、兼容性等，折叠或专家模式。
4. **工程证据**：canonical path、内部 ID、checksum、端口、策略表达式，仅治理/审计角色默认可见。

非技术页面的错误信息先回答“哪个业务目标未满足、在哪里修”；错误码只能作为次级证据，不能代替任务语言。

## 6. Gate A 验收问题

- [ ] 每个含混角色词已拆成可执行 Actor Card。
- [ ] 同一账号兼任角色时，仍能指出每项任务属于哪个角色工作台。
- [ ] 每个 Top task 都有目标角色、频率、复杂度预算和升级路径。
- [ ] Role–Task–Object、Role–Surface Access、Intent–System Translation 三张矩阵完成。
- [ ] IA 先声明工作台/受众边界，再声明对象组织原则。
- [ ] 系统底座对象没有未经论证直接升格为非技术用户导航。
- [ ] 能用目标角色的话复述所有阻断与修复动作；技术证据有明确披露层级。

任一项失败，不得进入 Gate C。
