# 服务蓝图（Service Blueprint）

> 服务协同层的产物。回答：谁在什么阶段，通过哪个端做什么；孩子/家长能看到什么，后台在发生什么。

## 1. 何时强制画

| 情境 | 是否强制 |
|------|----------|
| 多角色参与（孩子/教师/助教/家长 ≥2 类） | ✅ 强制 |
| 多端协同（学生端 Pad / 大屏 / 后台控制台 / 打印机 / 家长手机） | ✅ 强制 |
| 线上线下交接（课前准备、课后发送、打印交付） | ✅ 强制 |
| 纯单端设置页/账号页 | ❌ 不强制（用状态模型即可） |

## 2. 泳道（课堂产品示例泳道，可按需删减）

| 泳道 | 内容 |
|------|------|
| 孩子 | 孩子的动作与体验 |
| 主教 | 台前主导教师 |
| 现场支持助教 | 按责任组巡视、个体恢复与线下支持 |
| 后台履约助教 | 教室级生成、QC、播放、打印与交付任务 |
| 学生端 Pad | App 呈现与采集 |
| 大屏 | 共享级呈现 |
| 后台控制台 | 系统/后台位操作（QC/队列/发送） |
| 家长（触点） | 说明会/旁观/收短片/接娃 |

横轴 = 阶段（沿用 rundown 阶段流）；两条分界线：
- **可见线**：线上=孩子/家长可感知，线下=不可感知；
- **交接线**：角色间交接处用 → 标出（最容易断的点）。

## 3. 用法

1. 先按 [role-capability-and-surface.md](role-capability-and-surface.md) 完成 Actor Card；同一人兼任的角色仍使用不同泳道，除非任务、知识与决策权完全相同；A/B/C 等临时排班代号不得直接成为稳定 Actor；
2. 再按 rundown 阶段流摆时间轴，把各泳道动作填入；
3. 圈出**跨泳道交接点**（如“某位现场支持人员在 42' 完成未结事项交接后承担后台履约”、"中场=QC 窗口"），每个交接点必须回答：交接的触发事件是什么？谁接走未结事项？新责任何时生效？下游没就绪时的兜底是什么？
4. 检查**认知越界**：某泳道是否被要求理解不属于其 Actor Card 的 schema、策略、发布或运行细节；越界任务必须自动化、翻译或转交；
5. 检查**可见性倒挂**：孩子可见的事物，其后台依赖是否已在更早阶段就绪（如揭晓环节必须看到 QC 过的版本）；
6. 后台线的"时间窗"只作设计参考，不构成调度计划（时间解耦原则）。

## 4. 最小模板

```
阶段 →        阶段 0        阶段 1          阶段 2 …
孩子         入座破冰      听线索·悄悄话
主教         带规矩        讲述线索
现场支持助教  巡场          耳语兜底
后台履约助教  检查任务通道  接收节点产出 / QC
学生端 Pad   锁定待机      语音采集
大屏         拼贴墙        —
后台控制台   —             （收敛即预生成）
──────────── 可见线 ────────────
系统/数据    知情同意名单   悄悄话落库      缩略图生成/QC
```

## 5. 与既有模型的衔接（示例）

- 泳道动作引自 rundown 阶段表，不另造事实；
- 「台前/后台双线」（课程 rundown）是本蓝图的课堂段；
- 课前/课后段（Day0、生产线、发送窗口）从课程编辑的「课前/课后」块与课程基础字段取。

## 6. 稳定责任与人员排班必须分层

- Actor 泳道表达稳定的目标、决策权与任务语言；人员姓名、排班字母、临时兼任方式不进入 Actor 名称。
- 当人员比例或职责会随规模变化时，另建 staffing snapshot / assignment：记录“谁在什么时间、对哪个班级或责任组承担哪个角色”。
- 一人中途换岗画成两条带时间边界的 assignment 和一个 handoff，不把两个角色合成“复合助教”。
- 现场支持比例（如每 2–3 名孩子一人）属于服务容量 / 排班约束；后台履约位属于教室级责任要求。两者可以随业务版本调整，不应写死进课程节点或导航。
- 页面与权限读取当前有效 assignment；历史运行证据保留当时 actor 与责任 scope，不能因后来换岗而改写。
