# 真源与版本路由（Source Routing）

> Gate A 的第一步。任何模型动作前，先确认"采用哪些文档作为依据、哪些已退役"，防止把旧版本当真理源。

## 1. 文档分四类

| 类 | 含义 | 可否作为模型依据 |
|----|------|------------------|
| **现行基准** | 当前唯一有效的业务规格（路由表登记为"唯一基准"） | ✅ 必须以其为准 |
| **原始材料** | 业务方原始交付（交付包等），现行基准由此演化 | ✅ 用于溯源；与现行基准冲突时以基准为准 |
| **历史记录** | 某轮工作的设计文档/决策分析（成文时点正确，后被新基准覆盖部分口径） | ⚠️ 只作背景，不作依据；其中被新基准否定的部分明确忽略 |
| **被取代/存档** | 各类 `存档/`、`archive/` 归档目录 | ❌ 禁止引用（路由表已标注"勿引用"） |

## 2. 路由入口（通用约定）

| 范围 | 路由文档 |
|------|----------|
| 各需求域 | 该域 README 路由表 |
| 全项目导航 | `AGENTS.md` |
| 各模块 | 模块 `SKILL.md` |

## 3. 冲突处理规则

1. 同一主题只认路由表登记的**最新版本号**（如 课程A = v2.1-线索版、课程B = v2.0-过渡版）；
2. 历史记录中的口径被新基准否定的（如旧版适龄口径、旧线索设定），建模时视为**已退役**，但保留其历史事实（它解释了现状为何如此）；
3. 业务方材料内部矛盾（如上游材料对同一钩子给出两种说法）→ **原样还原，登记为"待业务方确认"**，不擅自修复；
4. 发现疑似过时口径时，先查路由表，再全局 grep 同类表述，**列出全部受影响位置**再处理（对应团队工作准则）。

## 4. 版本登记表（建模时随产物提交）

每个 Product Logic Spec 的 §1 必须附此表：

| Source ID | 文档 | 版本/地位 | 采用内容 | 冲突或疑问 |
|-----------|------|-----------|----------|-----------|
| 例：SRC-01 | 01-课程A-详细rundown.md | 唯一基准 v2.1 | 阶段流/线索/交付物 | — |
| 例：SRC-02 | （业务方材料） | — | — | 钩子链矛盾，待业务方确认（原样还原） |
